# Baselane mods marketplace: design

Date: 2026-10-05
Status: approved in conversation, waiting for review of this written spec

## 1. Goal

A public gallery of Claude Code mods, in the style of the Grafana dashboards site. Anyone can browse, search and filter mods. Each mod has its own page with screenshots, versions, what the mod can do, and a one-line install. Anyone can publish a mod after automated checks pass. Mods that Baselane reviewed carry a "Verified" badge.

This is a separate Baselane product line. It reverses the line "Out of scope for 12 months: ... a public marketplace" in `hq/STRATEGY.md:180`. Section 11 lists the HQ doc changes.

### Decisions made with the owner

| # | Decision |
| :- | :- |
| D1 | Separate product line, modeled on the Grafana dashboards gallery. |
| D2 | Open publishing. Automated checks gate every listing. Reviewed mods get a Verified badge. |
| D3 | Public gallery only. No private galleries, no paid mods, no revenue in the first version. |
| D4 | Authors submit by pull request to one catalog repo. |
| D5 | Static site on GitHub Pages. No server code. |
| D6 | Mods only. Every entry must contain mod hook code. It can also ship skills or commands. |
| D7 | The site is built by a zero-dependency Node script, with one pinned markdown library. |
| D8 | GitHub holds the CI run of every first-time contributor until a maintainer approves it. This is permanent. |
| D9 | The UI must be very good. It gets its own design phase and a measurable quality bar (Section 7). |
| D10 | claudemod.com is a UI reference, not a scope change. The design phase takes its good ideas (7.1). The scope stays mods only. |

### Nearest existing site

claudemod.com (checked 2026-10-05) is a community gallery for every Claude Code extension type: 155 items in 9 types. It has ⌘K search, category filters, a "Top Mods" list and a mascot. It shows no verification, no capability list and no one-line install, and each item links to its GitHub repo. It uses "mod" for every extension type, so visitors may expect our gallery to list skills and MCP servers too. The browse page and `/submit/` say in one line what a mod is and link to the Claude Code mods docs.

### Facts this design depends on

All from the Claude Code docs, read on 2026-10-04, or from a local run.

- Mods are generally available and on by default from Claude Code v2.1.287. No official mods gallery exists. Anthropic shares 3 sample mods in a playground repo.
- A marketplace is a git repo with `.claude-plugin/marketplace.json`. Users run `/plugin marketplace add <owner>/<repo>`, then `/plugin install <plugin>@<marketplace-name>`.
- `github` and `git-subdir` plugin sources take `ref` (branch or tag) and `sha` (a full 40-character lowercase commit SHA). With both set, Claude Code checks out `sha`.
- An entry accepts `category`, `tags`, `displayName`, `description`, `author`, `homepage`, `repository`, `license`, `keywords`, `version` and a free-form `metadata` object. Before install, users see only the entry's own fields for a non-relative source.
- Users get a new copy only when the plugin's computed version changes. `plugin.json` `version` wins over the entry `version`.
- `"forceRemoveDeletedPlugins": true` uninstalls a removed plugin from users' machines at session start. `"renames": { "<name>": null }` records a removal.
- Background auto-update is off by default for a user-added marketplace.
- `claude plugin validate <dir>` lists a mod's `hooks:`, `calls:`, `state writes:` and `state reads:` lines without running it. Verified locally on `cost-meter` with an empty home folder and no login.
- `claude plugin test <dir>` runs the mod's tests with no login. Verified locally on macOS: 11 pass. Not yet verified on a Linux GitHub runner (Section 12).

## 2. Architecture

One public repo, `baselane-sh/mods-catalog`.

```text
entries/<name>.json              one file per mod, written by the author
lock/<name>.json                 written by the bot only: SHA, version, capabilities, submitter
verified.json                    reviewed name and SHA pairs, maintainers only
schema/entry.schema.json         JSON schema for entries/*.json
schema/lock.schema.json          JSON schema for lock/*.json and the check result file
.claude-plugin/marketplace.json  GENERATED by the bot on main, never edited by hand
site/                            build script, templates, CSS, search JS
test/                            node:test suites and fixtures
.github/CODEOWNERS               maintainers own everything except entries/
.github/ISSUE_TEMPLATE/report.yml
.github/workflows/check.yml      pull_request, untrusted
.github/workflows/merge.yml      workflow_run, trusted
.github/workflows/publish.yml    reusable, plus push to main and a daily schedule
```

The marketplace `name` is `baselane-mods`. The `owner` is `{ "name": "Baselane", "url": "https://baselane.sh" }`. The site is at `https://mods.baselane.sh`.

The existing local repo `mods/` becomes the public repo `baselane-sh/mods`. Its own `.claude-plugin/marketplace.json` is renamed to `baselane-mods-dev`, so that it does not collide with `baselane-mods`. A user can register only one marketplace per name.

## 3. Data

### 3.1 Entry (written by the author)

`entries/<name>.json`. The file name must equal `name`.

| Field | Required | Rule |
| :- | :- | :- |
| `name` | yes | Matches `^[a-z0-9][a-z0-9-]{1,47}$`. Equals the `name` in the mod's `plugin.json`. |
| `source` | yes | A `git-subdir` source with `url` in GitHub `owner/repo` form plus `path`, or a `github` source with `repo`. `ref` is required and must be a tag. `sha` is not allowed: CI adds it. Only github.com repos are accepted. |
| `category` | yes | One of: `guard`, `pane`, `band`, `command`, `sound`, `style`, `stats`, `nudge`, `lifecycle`, `render`. |
| `tags` | no | 0 to 8 items. Each matches `^[a-z0-9-]{2,24}$`. |
| `screenshots` | no | 0 to 6 paths relative to the plugin folder. Each is `.png`, `.jpg`, `.webp` or `.gif` and is 2 MB or smaller. |

Example:

```json
{
  "name": "cost-meter",
  "source": { "source": "git-subdir", "url": "baselane-sh/mods", "path": "plugins/cost-meter", "ref": "v0.2.0" },
  "category": "band",
  "tags": ["cost", "usage"],
  "screenshots": ["docs/band.png"]
}
```

The mod's `plugin.json` must set `name`, `version` (semver), `description` (200 characters or fewer), `author` and `license`.

### 3.2 Lock (written by the bot)

`lock/<name>.json`:

```json
{
  "name": "cost-meter",
  "sha": "<40 lowercase hex>",
  "ref": "v0.2.0",
  "version": "0.2.0",
  "submitter": "<github login of the first PR author>",
  "hooks": ["tool.call", "session.start", "ui.render{component=AbovePrompt}"],
  "calls": ["$.clock.every", "$.session.usage", "$.ui.toast"],
  "testCount": 11,
  "listedAt": "<ISO date of the first listing>",
  "updatedAt": "<ISO date of this version>"
}
```

`submitter` is set once, when the entry is first listed, and never changes. The lock file's git history is the mod's version history.

### 3.3 Verified list

`verified.json` is an array of `{ "name", "sha", "reviewer", "date" }`. A mod shows the Verified badge only when its locked SHA equals the SHA in this list. When a mod updates to a new SHA, the badge drops until a maintainer reviews the new SHA. Only maintainers can change this file (CODEOWNERS plus branch protection).

### 3.4 Generated marketplace entry

For each entry, `publish` writes one `marketplace.json` entry:

- `name`, `category`, `tags` from the entry.
- `source` from the entry, plus `sha` from the lock.
- `version`, `description`, `author`, `license`, `homepage` and `repository`, copied from `plugin.json` at the locked SHA. Claude Code shows only entry fields before install, so the copy is needed.
- `metadata`: `{ "submitter", "verified": true|false, "hooks", "calls", "gallery": "https://mods.baselane.sh/mods/<name>/" }`.

Top level: `name`, `owner`, `description`, `"forceRemoveDeletedPlugins": true`, and `renames`.

`renames` is append-only. It holds every removed name mapped to `null`.

## 4. Submission pipeline

### 4.1 `check.yml` (untrusted)

- Trigger: `pull_request` on `main`.
- Permissions: `contents: read`. No secrets.
- `timeout-minutes: 10`. Concurrency group per PR, cancel in progress.
- Installs a pinned Claude Code version, then runs the rules below. It stops at the first rule that fails.

| # | Rule | Fails when |
| :- | :- | :- |
| R1 | Scope | The PR changes anything other than exactly one file under `entries/`. Maintainer PRs skip this rule. |
| R2 | Schema | The entry does not match `schema/entry.schema.json`. |
| R3 | Name | The entry `name` differs from `plugin.json` `name`. Or, for a new entry, the name equals a listed name or a `renames` key after we lowercase it and remove `-`, `_` and `.`. |
| R4 | Owner | The entry exists in `lock/` and the PR author is not its `submitter`. To move a mod to a new owner, a maintainer changes `submitter` in the lock file in a maintainer commit. Then the author runs the check again. |
| R5 | Ref | `ref` is not a tag on the source repo, or the repo is not public. CI resolves the tag to a full SHA. |
| R6 | Is a mod | `hooks/hooks.json` is missing, or validate prints no `hooks:` line. |
| R7 | Validate | `claude plugin validate` fails. CI records the `hooks:` and `calls:` lines. |
| R8 | Tests | `claude plugin test` fails, or it runs zero tests. |
| R9 | Update | For an existing entry, the `plugin.json` version is not higher (semver) than the locked version. Without a bump, users never receive the new code. |
| R10 | Size and shape | The plugin folder is over 10 MB, has a top-level `bin/`, has a symlink that points outside it, or a screenshot breaks the 3.1 rules. |

It always uploads one artifact, `check-report.json`: the PR head SHA and, for each rule, pass, fail or not run, with a fix hint for a fail. On success the report also holds the result: the fields of `schema/lock.schema.json` without `submitter`, `listedAt` and `updatedAt`.

On any result, a step in `merge.yml` posts or edits one PR comment from the report. The comment lists each rule with pass or fail and a fix hint. The bot edits the same comment on each run. It does not add a new one.

### 4.2 `merge.yml` (trusted)

- Trigger: `workflow_run` of `check.yml`, type `completed`.
- Runs main's own copy of the workflow. Never checks out or runs PR code.
- Permissions: `contents: write`, `pull-requests: write`, `actions: read` (to download the artifact from the check run).

Steps:

1. Post or edit the result comment (4.1).
2. Stop unless the check concluded `success`.
3. Check again, through the GitHub API, that the PR changes exactly one file under `entries/`. A PR that edits `check.yml` could fake a pass. This step blocks that.
4. Check that the PR head SHA equals the head SHA in the artifact.
5. Read `check-report.json` as data only and validate it against the schema.
6. Run `git ls-remote` on the mod's repo and check that the tag still resolves to the SHA in the artifact.
7. Squash-merge the PR.
8. Commit `lock/<name>.json`. Set `submitter` and `listedAt` on a new entry. Set `updatedAt` on every merge.
9. The push of the merge and the lock commit starts `publish.yml` through its `push` trigger. `merge.yml` does not call `publish.yml` directly, so publish runs once.

`merge.yml` and `publish.yml` commit and merge with a token from the Baselane catalog GitHub App (4.5), not with the built-in `GITHUB_TOKEN`. Branch protection blocks the built-in token. The app key is a repo secret. Only these two trusted workflows read it. `check.yml` has no secrets.

### 4.3 `publish.yml`

- Triggers: `push` to `main` (bot merges and maintainer commits), `schedule` daily at 03:00 UTC, and `workflow_dispatch`. A push that changes only `.claude-plugin/marketplace.json` does not start it again (`paths-ignore`).
- Permissions: `contents: write`, `pages: write`, `id-token: write`.

Steps:

1. Read `entries/`, `lock/` and `verified.json`.
2. For each lock, check that the SHA can still be fetched. Record failures in `health.json` (name and first failure date).
3. Fetch `plugin.json`, the README and screenshots at the locked SHA.
4. Fetch GitHub star counts through the API.
5. Write `.claude-plugin/marketplace.json` and run `claude plugin validate` on the repo root. Commit it if it changed.
6. Build the site into `_site/` and deploy it to GitHub Pages.

### 4.4 Maintainer path

A maintainer PR that changes more than one file (for example the launch seed) does not merge automatically, because step 3 stops it. For these, a maintainer runs `node site/lock.mjs <name...>` on their own machine. It runs R2 to R10 for each name and writes the lock files. The maintainer commits the entries and locks together and merges by hand. `publish` lists only entries that have a lock file and fails the build if an entry has no lock.

### 4.5 Repo settings

- A ruleset on `main`:
  - Require a pull request. Required approvals: 0, so the bot can merge a passing PR.
  - Require review from Code Owners. `CODEOWNERS` gives maintainers everything except `entries/`, so a PR that touches `verified.json`, `lock/`, `schema/`, `site/` or `.github/` needs a maintainer approval.
  - Require the `check` status.
  - No force push, no branch deletion.
  - Bypass list: the Baselane catalog GitHub App and the maintainers, so they can commit locks, `marketplace.json` and emergency takedowns.
- The Baselane catalog GitHub App: installed on this repo only, with contents and pull requests write.
- Fork PR workflow approval: "Require approval for first-time contributors" (D8). A maintainer reads the entry and the linked repo before they click "Approve and run".
- GitHub private vulnerability reporting: on.

### 4.6 Verified review

A maintainer reads the mod's code at the locked SHA. Then the maintainer adds `{ name, sha, reviewer, date }` to `verified.json` in their own PR. The review checks at least that each item in `calls` has a clear reason in the README, and that no network call sends session content anywhere the README does not state.

## 5. The gallery site

Static pages built by `site/build.mjs` (Node 22, no dependencies except one pinned markdown library).

### 5.1 Pages

| Route | Content |
| :- | :- |
| `/` | Browse. A one-line explanation of what a mod is, with a link to the Claude Code mods docs. A "Top mods" row: the 8 mods with the most GitHub stars. Search box, category filter, "Verified only" toggle, sort (newest, recently updated, most stars, name). A grid of cards: name, one-line description, category, author, version, update date, stars, Verified badge. Filter and sort state is in the URL query, so a link keeps it. |
| `/mods/<name>/` | Mod page. See 5.2. |
| `/submit/` | How to publish: steps, an entry template, the R1 to R10 rules in plain words, and how Verified works. |
| `/index.json` | The search index: name, description, category, tags, author, version, dates, stars, verified. |
| `/404.html` | Not found page. |

Search runs in the browser over `index.json`. It matches name, description and tags. ⌘K (Ctrl+K on Windows and Linux) opens a search palette on every page. Arrow keys move through the results, Enter opens a mod page, and Escape closes the palette.

### 5.2 Mod page

1. Header: name, description, author, version, category, stars, Verified badge.
2. Unverified warning, only when the mod has no badge: "Baselane has not reviewed this code. It runs with your permissions."
3. Install block with copy buttons:
   - `/plugin marketplace add baselane-sh/mods-catalog` (only once)
   - `/plugin install <name>@baselane-mods`
   - A note: turn on auto-update in `/plugin` > Marketplaces > baselane-mods, so that updates and takedowns reach you.
4. "What this mod can do": the `calls` and `hooks` lists in plain words, riskiest first. For example "Starts programs", "Makes network requests", "Sees every tool call", "Can approve or block tool calls". The raw lists are in a fold-out. The word mapping is a table in `site/capabilities.mjs`, built from the mods reference (Section 12). A call or hook that is not in the table shows as raw text, so nothing is hidden.
5. Screenshots.
6. The README at the locked SHA.
7. Version history from the lock file's git log: version, date, SHA link.
8. Links: source at the locked SHA, and "Report this mod" (a prefilled GitHub issue with the `report` label).

An entry that is in `health.json` for 3 or more days shows "Source missing" and does not appear on `/`. It stays in `marketplace.json`. Removal from `marketplace.json` uninstalls a mod from every user (`forceRemoveDeletedPlugins`), and only a takedown (6.1) does that.

### 5.3 Safety of author content

A README and its links are untrusted. We serve them on our domain.

- Markdown is rendered at build time. All raw HTML is escaped, not passed through.
- Links and images must use `https:`. Any other scheme is removed and the text stays.
- Relative image paths resolve to `raw.githubusercontent.com` at the locked SHA.
- Every page sets a Content Security Policy in a meta tag: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' https://raw.githubusercontent.com https://avatars.githubusercontent.com; object-src 'none'; base-uri 'none'`.

## 6. Takedown, reports and failures

### 6.1 Takedown

1. A maintainer deletes `entries/<name>.json` and `lock/<name>.json` and adds `"<name>": null` to `renames`.
2. `publish` writes the new `marketplace.json`, which has `forceRemoveDeletedPlugins: true`.
3. A user whose copy of the marketplace is current loses the mod at their next session start.

Limit: this reaches only users whose marketplace copy is current. Auto-update is off by default. The install block asks users to turn it on (5.2). The `/submit/` page and the mod page state this limit. We do not claim more.

Emergency path: a maintainer commits straight to `main`. Target: less than 1 hour from a confirmed report to removal.

A removed name stays reserved. R3 compares new names with the `renames` keys.

### 6.2 Reports

- "Report this mod" opens an issue from `.github/ISSUE_TEMPLATE/report.yml` with the `report` label.
- Security reports go through GitHub private vulnerability reporting.

### 6.3 Failure cases

| Case | Behavior |
| :- | :- |
| A check fails | The bot comment lists each failed rule and its fix hint. Nothing merges. |
| The author moves the tag after the check | Step 6 of `merge.yml` stops the merge. The author pushes a new commit to the PR to run the checks again. |
| A source repo or SHA disappears | `health.json` records it. After 3 days the entry shows "Source missing" and leaves `/`. |
| Code changes after review | Not possible. Every install is pinned to the checked SHA. |
| GitHub Pages is down | Installs still work. Claude Code reads the catalog from the repo, not from the site. |
| GitHub API rate limit during publish | Star counts keep their last values. The build does not fail. |

## 7. UI quality bar (D9)

### 7.1 Design phase

Before any page is built:

1. Use the `impeccable` design skill to set a visual direction for the browse page and the mod page.
2. Make mockups of both pages, light and dark, at desktop and phone width.
3. The owner approves the mockups.
4. After the build, an `impeccable` finish review compares the site with the approved mockups. Material differences are fixed before launch.

The direction must fit the baselane.sh brand. The design phase can propose a distinct look for the gallery, and the owner decides.

Reference: claudemod.com. The design phase must include its ⌘K search palette and its "Top mods" ranking (5.1), and must propose a brand character for the gallery. The owner decides if the character ships. The design must not copy its layout, art or copy.

### 7.2 Measurable bar

- Lighthouse 95 or higher for performance and accessibility on `/` and on one mod page, on mobile settings.
- Every control works with the keyboard alone, with visible focus.
- No layout shift when filters or sort change (CLS 0.01 or lower).
- Search results update in under 50 ms for 500 mods.
- Layout works from 360 px width up to desktop, with no horizontal scroll.
- Light and dark themes follow the system setting.
- WCAG 2.2 AA color contrast.
- No em-dashes in any UI text.

## 8. Testing

Write tests first, then the code. Use `node:test`, with no added dependencies. Following `mods/AGENTS.md`, prove each test can fail: break a copy of the code under test and confirm that a test fails.

- Rules R1 to R10: one fixture that passes and at least one that fails for each rule.
- Build: a golden test. Fixture entries and locks produce the expected `marketplace.json`, `index.json` and pages. `claude plugin validate` passes on the generated marketplace.
- README safety: fixtures with `<script>`, `<img onerror>`, `javascript:` links, `data:` images and raw HTML must come out escaped or removed.
- Capability mapping: each mapped call gives its words. An unknown call gives raw text.
- Workflow security, on a real test fork before launch:
  - A PR that edits `check.yml` and an entry does not merge.
  - A PR that changes two entries does not merge.
  - A PR that updates another author's entry fails R4 and does not merge.
  - A PR whose tag moves after the check does not merge.
  - A PR from a first-time contributor does not run until approved.
- Site: end-to-end tests by the `e2e-runner` agent: search, each filter, sort, URL state, the mod page, copy buttons, the unverified warning, and phone width. An axe accessibility scan. Lighthouse against 7.2.

## 9. Launch

1. Run a secret scan over the full history of `mods/`. Fix any finding before the repo goes public.
2. Rename the `mods/` manifest to `baselane-mods-dev`. Make the repo public as `baselane-sh/mods`. Tag the launch commit.
3. Create `baselane-sh/mods-catalog` with the settings in 4.5.
4. Seed the 61 existing mods in one maintainer PR through the maintainer path (4.4): 61 entries, 61 locks, and 61 rows in `verified.json`.
5. Add the CNAME record `mods.baselane.sh` and turn on Pages with HTTPS.
6. Install 3 mods from the live marketplace on a clean machine and confirm each one loads (`/plugin` shows `mods active`).

## 10. Out of scope for the first version
